---
name: code-quality-gate
description: Implement or repair code in a Code Quality Gate-enabled repository using failing acceptance tests, frozen quality standards, iterative audits, and a final merge gate. Use for code changes in this repository.
---

Use the existing quality.config.json and the Code Quality Gate MCP tools when available; CLI equivalents are below. Work within the user's requested change. Do not merge, publish, or contact external services unless the user authorized those actions.

Run CLI commands from the project root. Use `cqg` when it is on PATH; for a project-local installation, use `npx --no-install cqg` instead. The executable is bundled with code-quality-gate, so do not download a separate npm package named cqg. Green without a task resumes the task and configuration recorded by the accepted red phase.

1. Inspect the requirement, existing code, and configured checks. Configure real project tools if audit.checks is empty. At least one required acceptance check must write JUnit, including separate failure/error counts. Include every required static, coverage, mutation or other check that the project has configured. If CI is used, prepare .code-quality-gate/ci-setup.sh to install the project toolchain and dependencies in the generated Ubuntu workflow, using locked versions; this file is an adapter and should be protected in the task.
2. Write acceptance tests before implementing the behavior. Define the interface or minimal loading stubs if necessary so failures are assertions rather than missing modules. Include normal, boundary and error cases relevant to the requirement.
3. Create .code-quality-gate/tasks/<task-id>.json with version:1, a safe unique id, title, requirements (nonempty string array), testFiles and codeFiles (explicit relative files, any language), testChecks (required JUnit check ids), protectedFiles (test helpers and report adapters), and maxAttempts (default 12). Include all affected implementation files. The user-approved configuration and listed tests/adapters become frozen after red.
4. Record red with `cqg red <task-id>`. The expected failing assertions must be observed. A loading error, skipped test, tool failure or already-passing test does not establish red. Phase accepted=yes means the red evidence was recorded; its underlying audit should still show FAIL.
5. Modify implementation only. Run `cqg green --note "Describe the implementation change"` after each iteration. Read .quality/code-quality-gate/history.md and the latest Markdown/JSON report, compare measured metrics with earlier iterations, fix the failures, and repeat within the task budget. Never weaken tests, lower thresholds, change locked requirements/adapters, rewrite evidence, or replace a detector with canned numbers. Any further implementation change invalidates the last green snapshot until green is rerun.
6. Run `cqg gate` immediately before proposing completion or an authorized merge. A fresh audit and matching red/green snapshots are required. Commit .code-quality-gate/tasks, .code-quality-gate/evidence and .code-quality-gate/active.json with the implementation so CI can reproduce the final gate. Generated reports and run.lock remain untracked.

Use `cqg audit` for independent diagnostics; it does not establish test-first evidence. `cqg status` reports the last iteration and next action. Every workflow iteration writes .quality/code-quality-gate/latest.md plus an individual report.

When the task budget is exhausted, preserve the failed report and explain the unsatisfied condition; do not create another task id to reset the same work's budget. If the user stops or changes the task, respect that immediately. Local hashes detect accidental edits; trusted CI and repository rules are responsible for tamper resistance and merge enforcement. Do not claim that local evidence proves all requirements were tested or that an unconfigured branch rule is active.

History observations are appended by the tool. Describe your change with --note (or the MCP note field), but never manually edit history.jsonl or replace old metric values. Configure audit.history.metrics to select visible columns; display selection does not add a quality threshold. Missing/not-run metrics remain explicit.
